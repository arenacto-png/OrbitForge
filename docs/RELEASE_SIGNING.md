# Release signing and APK verification

## Keep release keys private

- Create a dedicated release/upload key in Android Studio's **Build → Generate Signed Bundle / APK** wizard, or with `keytool`.
- Store the keystore outside the repository in a private, backed-up location. Do not commit the keystore, passwords, signing properties, or recovery material.
- Keep the key alias and certificate fingerprint in a secure record. Losing the key may prevent updates to an app distributed under the same signing identity.
- Do not use the Android debug key for production releases. Debug keys are development credentials and may be regenerated by the SDK.
- OrbitForge does not configure release signing in Gradle or GitHub Actions. CI has no signing secrets and does not publish releases.

Example key generation (run locally; choose and store your own values securely):

```bash
keytool -genkeypair -v \
  -keystore "$HOME/orbitforge-release.jks" \
  -alias orbitforge-upload \
  -keyalg RSA -keysize 4096 -validity 10000
```

Do not paste passwords or private key material into ChatGPT, logs, issue comments, or source files.

## Verify an APK

On Linux/macOS with Android SDK Build Tools installed:

```bash
apksigner verify --verbose --print-certs app-release.apk
sha256sum app-release.apk # Linux
shasum -a 256 app-release.apk # macOS
```

On Windows PowerShell, calculate the file checksum with:

```powershell
Get-FileHash .\app-release.apk -Algorithm SHA256
```

Compare the certificate SHA-256 fingerprint with the expected release certificate from your secure record. A valid signature alone does not prove that the APK came from a trusted build; verify the fingerprint and checksum from a trusted source.

The CI workflow applies this verification to the debug APK only. It uploads `app-debug.apk` and `app-debug.apk.sha256` as a build artifact; it does not sign a production APK, create a GitHub Release, or distribute an app.
